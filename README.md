# 로또 분석 · 번호 선택 — GitHub Pages용

로또 6/45 전용 정적 웹페이지입니다. 번호 생성, 출현 빈도 분석, 회차 입력, JSON/CSV/Excel 가져오기, JSON 내보내기를 제공합니다. 페이지의 토큰 입력이나 GitHub Issues 동기화 기능은 없습니다. 서버·데이터베이스 없이 GitHub Pages에서 실행됩니다.

## 기존 버전에서 업데이트

저장소의 기존 `data/lotto.json`에 수집 자료가 있다면 이 ZIP의 빈 초기 파일로 덮어쓰지 마세요. 기존 자료 파일을 유지하고 나머지 코드를 교체하면 누락 회차부터 수집합니다. 처음 배포할 때만 포함된 초기 데이터 파일을 사용합니다.

## 처음 배포하기

1. ZIP을 압축 해제합니다. GitHub에서 기본 브랜치가 `main`인 저장소를 준비합니다. GitHub Free 사용 시 공개 저장소에서 Pages를 사용할 수 있습니다.
2. **압축 해제한 폴더 안의 내용물**을 저장소 최상위에 업로드합니다. `index.html`, `data`, `scripts`, `tests`, `.github/workflows/lotto-pages.yml`, `.nojekyll`이 모두 포함되어야 합니다. ZIP 자체나 바깥 폴더 하나만 올리면 실행되지 않습니다.
3. 점으로 시작하는 `.github` 폴더가 파일 선택창에서 보이지 않으면 GitHub의 **Add file → Create new file**에서 파일명을 `.github/workflows/lotto-pages.yml`로 입력한 뒤 제공된 파일 내용을 붙여 넣습니다. `.nojekyll`도 같은 방법으로 빈 파일을 만듭니다.
4. 저장소 **Settings → Pages → Build and deployment → Source → GitHub Actions**를 선택합니다. 별도 추천 워크플로 템플릿은 추가하지 않습니다.
5. **Actions → Lotto Pages → Run workflow → main → Run workflow**를 실행합니다. 업로드 직후 Pages 설정 전 실행이 실패했어도 이 단계에서 다시 실행할 수 있습니다.
6. 실행의 `Deploy` 단계에 나온 주소 또는 Settings → Pages의 사이트 주소를 엽니다. 휴대폰·태블릿·PC에서 같은 주소를 사용하세요. 최신 Chrome, Edge, Safari, Firefox를 대상으로 합니다.

GitHub 설정 기준: [공식 Pages 배포 안내](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).

## 자동 수집과 저장

- 일요일·월요일 한국 시간 오전 9:17에 공식 결과 수집을 시도합니다. 월요일은 재시도 용도입니다. `main`에 파일을 올리거나 수동 실행할 때도 수집합니다.
- GitHub Actions가 공식 페이지의 최신 회차를 확인하고, 1회부터 최신 회차까지 누락 회차를 순차 조회하여 공식 JSON 응답을 검증합니다. 결과는 `data/lotto.json`에 저장하고 저장소에 커밋한 뒤 같은 작업에서 페이지를 배포합니다. 개인 액세스 토큰은 필요하지 않습니다.
- 수집 도중 실패하면 기존 회차와 이번 실행에서 검증을 마친 회차를 유지하고 실패 상태를 사이트에 배포한 뒤 작업을 실패로 표시합니다. Actions의 빨간 표시만으로 사이트 배포까지 실패했다고 판단하지 말고 `Deploy` 단계와 사이트 상태를 함께 확인하세요.
- 현재 묶음에는 당첨 결과를 임의로 채워 넣지 않았습니다. 최초 실행은 1회부터 최신 회차까지 전체 이력을 수집합니다. 이미 보유한 회차는 건너뛰되 최신 결과는 다시 확인합니다. 응답에 여러 회차가 포함되면 함께 검증·저장합니다. JSON 조회는 실행당 최대 200회, 요청 사이 1.1초 간격입니다. 상한 도달·네트워크 오류 시 검증된 회차를 중간 저장하며 다음 실행에서 누락 회차부터 재개합니다. 공식 응답에서 요청한 회차가 없거나 기존 번호와 충돌하면 중단하고 오류를 표시합니다. 자동 수집 범위는 공식 사이트가 제공하는 자료에 의존하므로 전체 완료 여부는 화면의 누락 수로 확인하세요.
- 페이지의 **최신 파일 확인**은 이미 배포된 JSON을 다시 읽습니다. 공식 사이트를 직접 크롤링하거나 Actions를 즉시 실행하는 버튼이 아닙니다.
- GitHub 일정 실행은 지연·누락될 수 있고, 공개 저장소는 활동이 60일 없으면 일정 실행이 비활성화될 수 있습니다. Actions 탭에서 확인하고 다시 활성화하세요. [일정 실행 공식 안내](https://docs.github.com/actions/using-workflows/events-that-trigger-workflows#schedule)
- 브랜치 보호나 조직 정책으로 봇의 커밋이 차단되면 `Save collection state`가 실패할 수 있습니다. 해당 저장소 정책에 맞게 봇의 쓰기 또는 별도 배포 구조를 설정해야 합니다.

## 기기별 자료

`data/lotto.json`의 공식 결과는 모든 기기에 공통으로 배포됩니다. 직접 입력·수정·삭제한 회차는 해당 브라우저의 localStorage에만 저장됩니다. 수정한 회차는 공식 자료를 새로 읽어도 유지되고, 삭제한 회차는 해당 기기에서 숨깁니다. **이 기기 수정 초기화**로 공식 결과만 다시 표시할 수 있습니다.

직접 입력한 자료를 다른 기기로 옮기려면 **자료 내보내기 → 다른 기기에서 자료 가져오기**를 사용하세요. 모든 기기에서 개인 자료까지 실시간 공동 편집하려면 별도 인증 서버·데이터베이스가 필요합니다. 이 정적 버전에는 포함되지 않습니다. 이전 사이트의 브라우저 저장 자료는 주소가 달라 자동 이전되지 않으므로 먼저 내보내세요.

## 자료 형식

JSON은 이 페이지의 내보내기 파일 또는 아래 구조를 지원합니다. 숫자는 문자열이 아닌 JSON 숫자여야 합니다. 같은 파일 안의 중복 회차, 중복 번호, 범위 오류, 보너스 중복은 파일 전체를 거부합니다.

```json
{"draws":[{"round":1,"nums":[10,23,29,33,37,40],"bonus":16}]}
```

CSV/Excel은 첫 시트의 8열 `회차,번호1,번호2,번호3,번호4,번호5,번호6,보너스` 또는 맨 앞에 No 열을 추가한 9열을 지원합니다. 첫 행의 제목은 선택 사항입니다. CSV는 UTF-8의 단순 숫자 표를 사용하세요. 파일 크기는 최대 10 MB입니다. Excel 읽기는 [SheetJS 0.20.3 공식 배포본](https://docs.sheetjs.com/docs/getting-started/installation/standalone/)을 필요할 때 로드하므로 온라인 연결이 필요합니다. 번호 생성·JSON·CSV 기능은 이 라이브러리 없이 동작합니다.

## 알고리즘과 해석

- 기본값은 암호학적 난수와 편향 없는 정수 추출을 사용하는 무작위 선택입니다. 각 조합에서 중복 번호를 금지하고 한 번에 출력하는 동일 조합도 제거합니다.
- 포함·제외·합계 범위·조합 사이 공통 번호 수를 검증합니다. 제한 내에서 요청 개수를 확보하지 못하면 오류를 알리고 조건을 임의로 풀지 않습니다. 후보 검색 실패가 수학적 불가능을 뜻하지는 않습니다.
- 생일 번호 집중 회피는 1~31 번호가 5개 이상인 조합을 후순위로 배치하는 실험 옵션입니다. 실제 구매 분포를 알지 못하므로 공동 당첨 감소·기대 수익 개선은 검증되지 않았습니다. 기본값이 아닙니다.
- 과거 당첨 조합 제외와 번호 공통 수 제한은 취향 옵션입니다. 어떤 특정 조합도 과거 출현 때문에 다음 회차 확률이 변하지 않습니다.
- 6/45 조합은 8,145,060개입니다. 서로 다른 N게임을 같은 회차에 구매하면 1등 당첨 확률은 N / 8,145,060입니다. 번호 선택 규칙은 개별 조합의 당첨 확률을 높이지 않습니다.
- 출현 빈도 검정은 회차 내 비복원 추출을 반영해 Pearson 통계량에 44/39를 곱하고 자유도 44의 근사 분포를 사용합니다. 38회 미만은 p값 해석을 보류합니다. 이 검정은 번호별 주변 빈도만 보며 독립성이나 예측 가능성을 검증하지 않습니다.
- 월 예산은 1게임 1,000원, 52주/12개월로 환산해 초과 여부를 표시하는 계산 기능입니다. 결제·구매를 실행하거나 금액을 강제 제한하지 않습니다.

제작 환경의 공식 사이트 실접속은 시간 초과로 실패했습니다. GitHub 실행 환경에서의 실제 수집 성공과 최초 배포는 아직 확인하지 않았습니다. 공식 사이트의 응답 형식·접근 정책이 바뀌면 `scripts/collector.mjs`를 수정해야 합니다. UI에는 최근 수집 시도·성공 시각과 실패 사유를 표시합니다.

`index.html`은 단독으로도 번호 생성과 수동 자료 관리에 사용할 수 있지만, 자동 갱신을 사용하려면 이 묶음 전체를 배포해야 합니다. 개발 시 알고리즘은 HTML 안과 `scripts/algorithm.mjs` 양쪽에 동일하게 반영하세요. 테스트가 두 사본의 일치 여부를 확인합니다.


## 예측 성능 검증 — 이번 추가 기능

페이지의 **예측 가설 검증 → 보유 자료로 시계열 검증**으로 실행합니다. 연속된 최소 400회가 필요하며, 누락 또는 중복이 있으면 검증을 거부합니다. 분석 범위 선택은 출현 통계에만 적용하고 예측 검증은 전체 보유 자료를 사용합니다.

비교 방법은 사전에 고정한 세 가지입니다.

1. 누적 번호 빈도를 균등 확률 쪽으로 보정하는 방법.
2. 최근 100회 고빈도 번호의 출현 확률을 보정하는 방법.
3. 최근 100회 저빈도 번호를 선호한다는 가설.

빈도 확률 보정은 100회 분량의 균등 사전값을 더합니다. 45개 번호의 예측 출현 확률 합은 6이며, 저빈도 가설도 0~1 범위를 유지합니다. 이 수치는 번호별 주변 확률로, 특정 여섯 번호 조합의 공동 확률이 아닙니다. 보정 강도·구간 길이를 현재 평가 결과에 맞춰 자동 튜닝하지 않습니다.

첫 100회는 초기 학습에 사용하고 그 뒤부터 매회 직전 자료로 다음 회차를 평가합니다. 마지막 100회는 개발 구간과 분리하여 표시합니다. 마지막 구간에서도 이미 지난 회차 결과는 다음 평가 때 학습에 들어가는 순차 갱신 방식입니다. 미래 회차를 섞거나 전체 자료로 빈도를 만든 뒤 과거를 평가하지 않습니다. 방식의 근거: [시계열 교차검증](https://otexts.com/fpp3/tscv.html).

표에는 다음 두 지표를 제시합니다.

- 평균 일치 수: 예측 확률 상위 6개와 실제 6개가 겹치는 수. 경계에서 동점이면 그 번호 중 무작위로 선택했을 때의 기대 일치 수를 계산하므로 소수가 될 수 있습니다. 무작위 1게임의 이론적 평균은 6×6/45 = 0.8개입니다.
- Brier 오차: 각 번호의 예측 출현 확률과 실제 출현 여부의 제곱 오차를 45개 번호에 걸쳐 평균합니다. 낮을수록 좋습니다. 균등 확률 기준은 (6/45)×(39/45)입니다. 단순 빈도 과적합이 확률 예측을 악화시키는지 확인할 수 있습니다.

이는 1등 당첨률이나 실제 구매 수익률 검증이 아닙니다. 실제 과거 전체 자료를 확보하지 못했으므로 세 방법의 우열도 아직 확인하지 않았습니다. 시험에 사용한 인공 자료의 성능을 실제 로또 예측 성능으로 제시하지 않습니다. 기본 번호 생성기는 무작위 선택을 유지하고 검증 결과로 자동 전환하지 않습니다.

## 성능 향상을 검토하는 순서

1. 전체 회차 수집 완료와 원본 대조가 우선입니다. 데이터 누락·수정 오류는 모델 개선보다 먼저 제거해야 합니다.
2. 위 세 가지 고정 가설을 같은 회차에서 비교합니다. 전체 빈도뿐 아니라 최근 100회·300회 통계도 함께 확인합니다.
3. 평가 구간 결과를 보고 모델을 수정했다면 그 구간은 더 이상 미사용 검증 자료가 아닙니다. 변경한 규칙·설정·날짜를 고정하고 이후 실제 추첨 자료를 새 검증 구간으로 축적해야 합니다. 현재 페이지의 반복 실행은 이러한 사전 등록을 자동 보장하지 않습니다.
4. 여러 방법·구간을 시도해 최고 결과만 선택하는 행위를 피합니다. 정식 우위 판정에는 평가 전에 비교 수와 판단 기준을 정하고, 회차별 오차 차이의 불확실성 및 다중 비교를 고려한 별도 검정이 필요합니다. 현재 표에는 유의성 검정이나 개선 판정을 제공하지 않습니다.
5. 독립 검증에서도 균등 기준을 일관되게 이기는 증거가 없으면 모델 복잡도를 높여 추천 번호를 바꾸지 않습니다. 신경망·번호 쌍 빈도·미출현 기간 등 특징을 많이 추가하는 것만으로 예측 성능이 향상되지는 않습니다.

공정하고 독립적인 6/45 추첨에서 과거 결과는 다음 회차 특정 조합의 확률을 바꾸지 않습니다. [동행복권 공식 안내](https://www.dhlottery.co.kr/lt645/intro)는 1등 확률을 1/8,145,060으로 안내합니다. 전체 이력을 확보하는 목적은 자료의 완전성과 검증 품질 향상이며, 예측력 확보를 보장하는 것이 아닙니다.

## cron-job.org와 연결할 때

현재 묶음은 기존 GitHub Pages 배포 구조를 유지합니다. 별도 수집 서버는 포함되어 있지 않습니다. 외부 예약 호출을 사용하려면 cron-job.org에서 GitHub의 수동 실행 API를 호출할 수 있습니다. 이 경우 예약은 외부에서 하지만 실제 수집·배포는 Actions에서 실행되므로 실행 대기 시간은 남습니다. 전체 수집을 cron-job.org의 한 HTTP 요청 안에서 직접 수행하지 않습니다.

- 기존 `.github/workflows/lotto-pages.yml`의 `schedule` 블록을 삭제하여 중복 예약을 피합니다. `workflow_dispatch`는 유지합니다.
- GitHub에서 대상 저장소만 선택한 fine-grained token을 발급하고 Actions: write 권한을 설정합니다. 토큰은 cron-job.org의 요청 헤더 설정에만 넣고 HTML·저장소·공개 URL에 넣지 않습니다.
- 요청 방식: `POST`
- 호출 주소: `https://api.github.com/repos/OWNER/REPO/actions/workflows/lotto-pages.yml/dispatches` (`OWNER`, `REPO`를 실제 값으로 변경)
- 헤더: `Authorization: Bearer 발급한토큰`, `Accept: application/vnd.github+json`, `Content-Type: application/json`, `User-Agent: lotto-scheduler`
- 본문: `{"ref":"main"}`
- 시간대: `Asia/Seoul`, 예시 일정: 일요일·월요일 오전 9:17.
- HTTP 성공은 실행 요청 접수만 뜻합니다. 실제 수집 완료 여부는 Actions 로그와 페이지의 수집 상태에서 확인합니다. 토큰 만료 시 교체해야 합니다.

근거: [GitHub workflow dispatch API](https://docs.github.com/rest/actions/workflows#create-a-workflow-dispatch-event), [cron-job.org](https://cron-job.org/en/faq/).
